# Registro de ventas con carrito, pago y comprobante imprimible

La implementación compone selección, carrito en centavos, registro RPC y comprobante A4 mediante impresión nativa. Los formularios rápidos reutilizan los modales compartidos y la RPC conserva la autoridad sobre precios, totales y snapshots. `npx vue-tsc --noEmit` termina correctamente, pero una venta confirmada en base de datos se presenta como fallida porque la respuesta real no coincide con el parser del cliente. **Watch for:** [confirmed] el desacople RPC/parser puede duplicar ventas al reintentar; [confirmed] los autocompletes pierden referencia visual y el diálogo no contiene el foco con teclado; [confirmed] un fallo de impresión solo llega a consola; [confirmed] no hay pruebas automatizadas del flujo nuevo.

## High-level view

El cliente envía únicamente IDs, cantidades y monto ingresado, y la RPC reconstruye los valores autoritativos. [confirmed] Su JSON anida la cabecera bajo `venta` y el cliente bajo `cliente`, mientras el parser busca ambos en la raíz y rechaza toda respuesta exitosa.

[confirmed] Los autocompletes admiten flechas, Enter y Escape, pero no desplazan a la vista la opción activa cuando el catálogo supera la altura del desplegable.

[confirmed] El diálogo de éxito asigna foco inicial, pero Tab puede llevarlo al dashboard oculto visualmente y Escape deja de funcionar desde allí.

El comprobante se construye con la respuesta RPC y el snapshot local del efectivo, fuera del modal y visible solo al imprimir. [confirmed] Si `window.print()` falla, la interfaz no muestra el error previsto.

[confirmed] La única validación ejecutada es estática; no hay pruebas que ejerzan el contrato JSON, pagos, carrito, teclado o impresión.

## Contrato RPC incompatible después del commit

[confirmed] `parseVentaRegistrada` en `app/composables/useVentas.ts` lee `id`, `cliente_id`, `cliente_nombre` y `cliente_celular` desde el objeto raíz. `registrar_venta` devuelve la cabecera como `venta` y el cliente como `cliente`, dejando en la raíz solo ítems, totales, estado y fecha. El parser retorna `null` después de que PostgreSQL ya insertó cabecera e ítems; `registrarVenta` muestra un rechazo genérico y conserva el formulario para reintentar.

```text
Registrar venta
      |
      v
RPC inserta y confirma ----> { venta, cliente, items, ... }
                                      |
                                      v
                         parser busca id/cliente_id en raíz
                                      |
                                      v
                    UI muestra fallo y permite reintentar
                                      |
                                      v
                         segunda venta potencialmente insertada
```

El parser debe alinearse con el contrato anidado y el caso necesita una prueba con un fixture idéntico al JSON de la RPC. El cast manual de `useSupabaseClient` oculta esta diferencia al type-check; un fallo de interpretación posterior a una respuesta exitosa tampoco debería presentarse como si la transacción hubiera sido revertida.

## Opción activa fuera de vista en catálogos largos

[confirmed] `AutocompleteCliente.vue` y `AutocompleteProducto.vue` actualizan `activeIndex`, pero no desplazan el elemento activo dentro del contenedor `max-h-64`. Al avanzar fuera de las opciones visibles, `aria-activedescendant` cambia mientras la lista permanece arriba, dejando sin referencia visual qué elegirá Enter. Cada cambio de índice debe llevar la opción activa a la vista con `scrollIntoView({ block: 'nearest' })`.

## Foco escapable del diálogo de venta exitosa

[confirmed] `VentaExitoModal.vue` enfoca `Imprimir PDF`, pero no contiene Tab ni vuelve inerte el dashboard. El foco puede alcanzar controles cubiertos y, al quedar fuera del contenedor, `keydown.esc` ya no recibe Escape. El modal debe atrapar y restaurar el foco, o usar un `dialog` gestionado que bloquee el fondo.

## Fallo de impresión invisible para el vendedor

[confirmed] `imprimir()` captura excepciones de `window.print()` y solo ejecuta `console.error`. El vendedor no recibe el error amigable y accesible previsto cuando la impresión no puede abrirse. El fallo debe alimentar un estado visible con `role="alert"` y comprobar la disponibilidad de `window.print`.

## Flujo crítico sin pruebas de comportamiento

[confirmed] No se encontraron pruebas dirigidas a `useVentas`, `parseVentaRegistrada`, carrito, autocompletes o impresión. El type-check no valida el JSON que cruza la frontera Supabase. La cobertura mínima debe fijar el contrato anidado, los cuatro estados de pago, cantidades, preservación tras rechazo, teclado con scroll y contenido del comprobante.
